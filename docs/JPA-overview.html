1. The layers of the application

A request travels top to bottom; the answer travels back up. Each layer has exactly one job. The exercises replace the bottom two layers (a CSV file and an in-memory list) by a real database.

Java / Spring Database Error handling
Rule of thumb: the controller never talks to a repository directly, and entities never leave the service layer as JSON (from chapter 12 on, DTOs and forms are used instead).

4. From class to table — two mappings that need a closer look

a) One table, two classes — Address is not an entity: its fields become extra columns of COMPANIES.

b) Composite primary key — an enrolment is identified by session number + enrolment number in that session. The key columns live in a small @Embeddable class, and @MapsId says that the session association supplies the E_SNO part.

Cancelled? The database stores a letter ('C') or NULL in SCANCEL / ECANCEL. The solution maps it as a String cancelFlag and derives isCancelled() from it, so queries can simply say where scancel is null.

Start with the simplest one that works. Every repository extends JpaRepository<Entity, IdType>, which already gives findAll(), findById(), save(), deleteById() … without writing any code.

6. Adding a person (exercise 11.2)

The same service method handles all three cases from the exercise: new company, existing company, no company.

7. Enrolling for a session — transaction and rollback (exercise 13.5)

All steps run in one transaction. If any check fails, an EnrolException is thrown and the database is put back exactly as it was — including a person that was inserted in step 1.

Testing tip. A test method marked @Transactional is rolled back automatically after it finishes, so the test data never reaches the database and tests stay independent (no @Order needed). Tests that exercise the transaction of the service itself (cancel, enrol) must not be @Transactional, so they clean up after themselves.
